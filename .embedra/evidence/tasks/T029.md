# T029 Evidence — ESP32-C3 RISC-V Provider

## Status

`COMPLETE` on 2026-09-25. T030 is next.

## Inputs and decisions

- esptool 5.4.0 identifies ESP32-C3 as image chip ID 5.
- ESP-IDF v6.0 revision `662a3be354759d9487bf4b1a629fadb766cb1800`
  supplies the C3 memory map, ROM linker definitions, and peripheral headers.
- Ghidra 12.1.3 supplies `RISCV:LE:32:default` with compiler specification
  `gcc`; the provider uses two-byte RV32IMC instruction alignment.
- Espressif SVD revision `be20aa12560889d6125d144cdb48cf615ac17628`
  is Apache-2.0. Its C3 data has shared-name address conflicts with the pinned
  ESP-IDF headers, recorded as `record-conflicts-prefer-svd` rather than hidden.

## Implementation and test evidence

- Added an Apache-2.0 freestanding C3 fixture generator, a pinned 65,600-byte
  binary and independent esptool/readelf/JSON oracles.
- Added the chip registry entry and provider-owned DROM, IROM, IRAM, DRAM, RTC,
  language, entry, and one-CPU RV32IMC topology decisions.
- Recognized esptool's checksum-covered address-zero flash-alignment segment and
  omitted it from mapped program memory.
- Added 1,902 ROM symbols, 46 peripheral windows with 1,053 header register
  addresses, and 37 SVD peripherals with 2,606 registers and 5,020 fields.
- Added provider, fixture, pack, architecture-boundary, and raw/enriched real
  Ghidra tests. The common loader, mapper, resolver, entry validator, and import
  service have an explicit regression check forbidding Xtensa assumptions.

## Verification

Focused unit and real-Ghidra tests passed. The complete quality, fixture,
handoff, exact-package, and reproducibility results are recorded in
`.embedra/evidence/commands.jsonl` and the final artifact fields in
`.embedra/state.json`.

## Support boundary

This supports generic ESP32-C3 application images with chip ID 5. It does not
claim exact silicon/package variants, C3 full-flash layouts, ULP firmware,
bootability, or hardware verification.
