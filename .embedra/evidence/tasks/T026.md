# T026 — Authoritative ESP Catalog

## Status

`COMPLETE` on 2026-09-23.

## Objective

Build the authoritative ESP SoC/part/module/board catalog generator,
provenance snapshot, exact-variant resolver, and CI drift detection for every
official ESP32-branded series present at generation time.

## Requirements and Prerequisites

- Requirements: US4; CORE-003, CORE-006, CORE-007, CORE-010, CORE-013,
  CORE-017 through CORE-021; ESP-015 through ESP-020; TOPO-001 through
  TOPO-005; TEST-001, TEST-005, TEST-007, and TEST-009.
- Prerequisites: T001 through T025 and the approved ESP32-S3 full-flash gate.
- Current repository state: T001 through T025 are complete. T025 and its gate
  remediation remain intentionally uncommitted and match the durable handoff.

## Expected Changes

- Pinned authoritative Espressif source metadata and generated catalog data.
- Versioned ESP catalog schema and pure catalog/resolver models.
- Deterministic generator and drift checker with resource/cancellation limits.
- Tests for exact variants, profiles, topology, deterministic ordering,
  malformed sources, ambiguity, provenance, and additions/removals/changes.
- Build/CI validation, user documentation, support matrix, and an ADR.

## Test and Fixture Plan

1. Write failing tests requiring every mandatory official ESP32 series and
   exact website-listed SoC variant.
2. Require modules and development boards to be profiles referencing exact
   silicon rather than processor records.
3. Test Xtensa/RISC-V, core-count, ULP/low-power, ROM, memory, security, and
   lifecycle fields without promoting `PLANNED` parts to verified support.
4. Test exact, ambiguous, and unknown resolution; variant support must never
   inherit from siblings.
5. Test deterministic generation, pinned-source digests, schema validation,
   cancellation/limits, malformed HTML/metadata, and drift classification.
6. Run unit, malformed-input, regression, packaging, and continuity suites.

## Vendor Data and Licensing

- Official Espressif SoC, module, and development-board catalog pages provide
  public product facts. Only normalized factual fields are retained; page
  markup, images, prose, and purchase links are not redistributed.
- Pinned ESP-IDF Apache-2.0 metadata supplies supported target identifiers,
  firmware chip IDs, ISA classification, and machine-readable SoC capability
  evidence where present.
- Every generated artifact will retain source URLs, exact content digests or
  Git revision, transformation identity, and redistribution disposition.

## Assumptions and Risks

- Official product facts are fragmented across catalog pages, datasheets, and
  ESP-IDF. Unknown fields remain explicit rather than inferred from a name.
- A module/board may list more than one compatible exact silicon variant; the
  resolver must preserve that ambiguity until authoritative ordering data or a
  user assertion identifies one.
- Website drift is detected against pinned normalized facts; normal builds do
  not require network access.

## Implementation Decisions

- Vendor HTML is never committed or packaged. The source snapshot retains only
  normalized factual fields plus exact hashes/revision and transformation.
- Silicon, modules, and boards use separate kinds. Profiles refer only to exact
  silicon record IDs; multiple candidates remain visible rather than guessed.
- The detached catalog checksum is validated before bounded JSON parsing.
  Closed keys, relationship integrity, topology consistency, support states,
  limits, and cancellation are validated before resolution.
- The common `DeviceCatalogSnapshot` projection includes exact silicon only;
  module/board profiles remain non-device records.
- Normal builds and installed use are offline. The scheduled/manual drift job
  is an explicit network workflow and emits candidate normalized facts only
  when review is required.

## Limitations

- Catalog presence is not provider verification. T027 through T031 remain
  responsible for shared services, each ISA/provider, fixtures, packs, and the
  ESP-family gate.
- The pinned ESP-IDF snapshot has no target/chip-ID metadata for ESP32-E22 or
  ESP32-S31; their website-documented ISA/core count is retained while firmware
  chip ID remains `UNKNOWN`.
- Exact ROM identities are not available in the selected catalog sources and
  remain `UNKNOWN`; no ROM relationship is inferred from a marketing name.
- Some module/board ordering profiles list multiple compatible exact silicon
  records. Resolution remains ambiguous until authoritative ordering evidence
  or an explicit user assertion selects one.
