# T034 Evidence — STM32 ELF/AXF and Intel HEX address-bearing inputs

## Status

`COMPLETE` on 2026-09-30. T033's deterministic goldens and the 53-part
selected catalog are the input. No STM32 exact part is promoted from `PLANNED`.

## Approach

Use Ghidra 12.1.3's native `ElfHeader`, `IntelHexRecordReader`, `ElfLoader`,
and `IntelHexLoader` for format parsing and import. Retain a pure, immutable
STM32 input model recording encoded addresses, sections, and native-loader
handoff facts. Test both the model and actual native Ghidra imports against
T033 goldens; keep part selection and raw-BIN base inference for later tasks.

## Implementation

- Pure `Stm32AddressedInput`, `Stm32ElfInput`, and `Stm32IntelHexInput`
  records hold encoded 32-bit address facts and immutable source positions.
  ELF virtual and physical segment addresses, sections, and entry are distinct;
  Intel HEX type 02/04 bases and type 03/05 starts remain encoded facts.
- `Stm32AddressedInputInspector` recognizes magic or record syntax independent
  of a filename. It delegates ELF and HEX syntax to the bundled Ghidra native
  readers, bounds input and object counts, checks source and address ranges,
  rejects malformed records, and identifies the corresponding native loader.
  It creates no Ghidra memory blocks and makes no exact-part inference.
- Headless tests call `ElfLoader` and `IntelHexLoader` directly with explicit
  Cortex language settings because the headless test process has no loader
  registry. This exercises Ghidra's native import implementation.
