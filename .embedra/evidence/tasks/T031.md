# T031 Evidence — ESP Product Profiles and ESP8266 Legacy Provider

## Status

`IN_PROGRESS` on 2026-09-28. Implementation and focused verification pass;
documentation and the final reproducible build gate remain.

## Implemented boundary

- Catalog callers can resolve silicon, modules, boards, or all product profiles
  through separate typed APIs. Profile-to-silicon projection follows only the
  explicit `siliconRecordIds`; a module or board name cannot satisfy the
  silicon-only resolver.
- ESP8266 is implemented in separate `formats.esp8266`, `targets.esp8266`, and
  `ghidra.esp8266` packages. It is absent from the ESP32 chip-ID registry and
  provider resolver.
- Version 1 and version 2 fixtures were generated from repository C/linker
  sources with xtensa-lx106-elf GCC 10.3.0 and esptool 5.4.0. Two generations
  produced byte-identical fixtures and oracles; provenance validation passes.
- The v2 IROM segment retains its unresolved encoded address. The Ghidra loader
  requires an explicit, validated flash base and records it as program
  provenance. The image format cannot distinguish ESP8266EX from ESP8285, so
  the provider records only the legacy family identity.
