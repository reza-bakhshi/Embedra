# T042 Evidence — STM32 board profiles for external memory and boot offsets

## Status

`COMPLETE` on 2026-10-02. T042 adds digest-pinned, reviewed STM32 board
profiles that layer external flash/RAM and boot offsets over an exact MCU record
without mutating any MCU pack. A pure board model, a digest-checked catalog, and
a composition planner pair board facts with the T039 `Stm32MemoryPlanner.Plan`
and fail closed on every missing, ambiguous, overlapping, or out-of-space fact.
Every one of the 53 curated exact parts remains `PLANNED`, the T039 memory
plans and T040 device-data packs are unchanged, and T043 is not started.

The repository builds 271 unit tests, 93 real-Ghidra integration tests, 112
STM32 Python tests (2 documented optional-source skips), and 4 ESP Python
tests. The reproducible gate passes with two clean, uncached 22-action builds
and a byte-identical 4,002,516-byte extension ZIP, SHA-256
`49486842fd383d6a48cc725abea402ab61ca1052a02bb6f082cfe4793ceb2c5d`.
The digest is also recorded in `.embedra/state.json`.

## Scope and invariants

- The pure/adapter boundary holds: `Stm32BoardProfile`, `Stm32BoardCatalog`, and
  `Stm32BoardPlanner` live under `targets`; no Ghidra API is imported.
- A board profile never mutates or extends an MCU pack. External flash/RAM and
  boot offsets are additive board facts. T039 `memory-plans.json`, the T040
  device-data packs, the applicability artifact, and the T041 vector behavior
  are unchanged.
- Every device-support state remains `PLANNED`. A board profile never promotes
  MCU or board support and never infers an exact part from a family or wildcard.
- No external size, address, boot offset, or board-to-part link is invented.
  A profile with no pinned fact stays explicit as `UNAVAILABLE` with a reason.
- The board snapshot is digest-pinned and cites the exact pinned BSD-3-Clause
  ST BSP revision and the pinned CMSIS device header for every memory-mapped
  CPU base; raw vendor sources are not redistributed.

## Implemented model

### Pure board-profile model

- `Stm32BoardProfile` separates board identity, category, the exact part link,
  the pinned per-board BSP provenance, the pinned board-index source, the CMSIS
  family, memory-mapped external regions, and explicit boot offsets. Reviewed
  profiles validate a non-empty board, sources, regions, and no reason;
  unavailable profiles validate a reason and no data.
- `ExternalRegion` records a device, controller, the quoted `startEvidence` and
  `sizeEvidence`, a positive size, and a distinct `ext-mem` address space, so a
  physical board range is never confused with a CPU address or a flash source
  offset. Overlapping external regions, duplicate ids, a non-`ext-mem` space, a
  zero size, or a size beyond the 32-bit space fail closed.
- `BootOffset` is kept separate from a CPU-mapped address.

### Digest-pinned catalog

`Stm32BoardCatalog` verifies the snapshot SHA-256
`78a3e0e41cc14585ad3c4140aed80fff6d53fcd367d6beec3d2cc787950c75f3`, the
curated selection digest, the reviewed board-index digest
`2b9c7c2cc5e2838c50190a507cc0d96792d3a3e5eba8a5aee4e21d50cc77b6a7`, and every
record's closed schema before exposing profiles. A profile resolves to an MCU
only by its explicit exact part id; a family, wildcard, or neighbouring board is
never substituted, and the reviewed count must match the recorded value.

### Plan composition

`Stm32BoardPlanner.compose` pairs a validated `Stm32MemoryPlanner.Plan` with one
reviewed profile and returns a new view; the underlying MCU regions, aliases,
and topology are never modified. It fails closed with a stable diagnostic on an
unavailable profile (`BOARD_NOT_AVAILABLE`), a part mismatch
(`BOARD_PART_MISMATCH`), an external region that overlaps an MCU region or
another external region (`EXTERNAL_REGION_OVERLAP`), a region beyond the 32-bit
space (`EXTERNAL_REGION_OUT_OF_SPACE`), or a boot offset outside every external
region (`BOOT_OFFSET_OUT_OF_RANGE`). External regions are tagged with a distinct
`ext-mem` space for reporting, while true numeric collisions are still compared
and rejected.

### Ghidra adapter boundary

Mapping external memory into a program is deliberately out of scope for T042.
The task keeps the pure plan and documents the boundary rather than guessing
memory permissions for external regions that are not present in the input.
No Ghidra adapter is added, so no integration test changes are required.

## Preserved boundaries and limitations

- T039 memory plans and the T040 device-data packs are not modified.
- All 53 curated parts remain `PLANNED`; T042 promotes no support state.
- The reviewed set covers nine boards. Boards whose external facts are not
  pinnable are either explicitly unavailable or simply absent; none is guessed.
- The U5 HSPI PSRAM window is not materialized because the pinned CMSIS header
  used here defines no memory-mapped HSPI alias; the U5G9J-DK1 profile therefore
  ships only its OCTOSPI1 NOR. The L552E-EV NOR and HyperRAM both map on
  OCTOSPI1 and are left explicitly unavailable rather than assigned an invented
  window.
- No Ghidra external-memory mapping is performed; no memory permission is
  invented.
