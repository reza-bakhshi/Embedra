## Implementation

- Planning validates the entire partition table before extraction and requires
  a valid chip-ID-9 bootloader at the documented merged-flash offset zero.
- Exact encoded image ends are derived within their containing ranges before
  the complete existing parser validates each bounded slice. Diagnostics are
  translated to physical flash source offsets.
- Bootloader, factory, OTA, and other unencrypted app entries are independent
  executable plans. Data, custom, and encrypted partitions remain exact opaque
  artifacts and encrypted bytes are never mapped as instructions.
- The loader creates application programs before the bootloader, maps every
  program through the shared workflow in its own rollback-capable transaction,
  cleans up newly created unsaved programs on failure, and writes no extracted
  files without an explicit destination.
- Each created program records full-flash SHA-256, partition-table offset,
  executable physical offset/length, role, and partition label in the mapping
  transaction.

## Verification and limitations

The clean configured build passed 107 unit and 13 real-Ghidra integration
tests across all 19 requested actions. Two subsequent configured builds
produced a byte-identical 274817-byte extension ZIP with SHA-256
`62dfbaf6c8910be600091a6ff1b95316e59843896858e9044c49d0d595d471a1`.

Support remains `EXPERIMENTAL`: fixtures are synthetic, no physical device
dump is verified, exact ESP32-S3 variants are not cataloged, active OTA
selection is not performed, and opaque partition interpretation/decryption is
outside T020. T021 must introduce explicit handlers and tests; it has not been
started.
