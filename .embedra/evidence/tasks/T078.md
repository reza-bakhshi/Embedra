## 5. Design decisions and provenance

- SHA-256-only verification: PGP signature verification would introduce a
  network dependency (keyserver lookups) that SpecKit's offline guarantees
  forbid; SHA-256 pins every artifact bit-exactly, and the auditor rejects
  any future PGP/trusted-key or metadata-skip entries.
- The SBOM records the *shipped* composition truthfully (no third-party
  runtime libraries) while still enumerating every Gradle-locked build-time
  component as `excluded`, satisfying "cover all bundled runtime
  dependencies and transitive libraries" without implying unsupported
  distribution scope.
- Dist side artifacts live in the git-ignored `dist/` release staging area:
  they are release-bundle outputs produced by the release gate, not
  committed repository content, matching SpecKit §12.2's per-release
  checksum/SBOM requirements (T079 will assemble them into the final
  bundle).
- Secret scan scope decision: emails inside copyright/attribution lines are
  vendor provenance that redistribution keeps deliberately; everywhere else
  an email is a finding. The 11 allowlisted hits are all synthetic CTF
  detection placeholders inside test sources, each justified inline.

## 6. Limitations

- Verification metadata covers resolvable Maven Central artifacts; the
  Ghidra framework jars (provided by the pinned host installation) and the
  wrapper distribution are integrity-checked by their own mechanisms
  (`verifyProjectScaffold` pins the wrapper version; the license audit
  byte-identifies Ghidra-derived language files) rather than by module
  verification metadata.
- The SBOM does not emit a per-file component for every pack content file
  (their per-file SHA-256 values are pinned inside each pack manifest and
  verified there; the SBOM carries the aggregate `contentDigest` per
  pack).
- SPDX format is not produced; CycloneDX 1.5 is the single mandated format
  for the release bundle.
