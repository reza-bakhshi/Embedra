# T044 Evidence — STM32 TrustZone secure/non-secure regions and veneers

## Status

`COMPLETE` on 2026-10-02. T044 adds a pure, evidence-gated STM32 TrustZone
security-domain layer: a deterministic generator and digest-pinned snapshot
(`catalogs/stm32/2026-09-29/security-domains.json`), a digest-checked catalog
loader, a non-mutating composer over the validated T039
`Stm32MemoryPlanner.Plan`, and a bounded veneer evaluator. Nineteen exact parts
carry pinned secure alias apertures; the other 34 stay explicitly `UNAVAILABLE`
with a reason and no window. Secure/non-secure partitions and non-secure-callable
boundaries remain configuration-dependent and are never guessed. All 53 curated
parts remain `PLANNED`; T039 memory plans, T040 device-data packs, T041 vector
behavior, T042 board profiles, and T043 signature packs are unchanged. No
Ghidra adapter is added (`NO_ADAPTER_PURE_PLAN_ONLY`, as T042 did).

The reproducible gate passes with two clean, uncached 22-action builds and a
byte-identical 4,256,466-byte extension ZIP, SHA-256
`9b3ab2e3577786a6b37f39d038eec16d5c0b7b71375c48ecc8a7f2f1d3e623f6`.
Repository tests: 316 unit, 93 real-Ghidra integration, 131 STM32 Python (4
documented optional-source skips), and 4 ESP Python tests.

## Scope and invariants

- The pure/adapter boundary holds. `Stm32SecurityAttribute`,
  `Stm32SecurityHeaderSource`, `Stm32SecurityWindow`, `Stm32VeneerTransition`,
  `Stm32SecurityRecord`, `Stm32SecurityCatalog`, `Stm32SecurityPlanner`, and
  `Stm32VeneerPlanner` live under `targets.stm32.security`; no Ghidra API is
  imported, and no `ghidra` mutation is added.
- STM-010: secure/non-secure images are represented only where the pinned
  per-exact-part evidence fixes them. The pinned CMSIS headers fix the secure
  alias *bases* (`*_BASE_S`) and their `*_BASE_NS` counterparts; the reviewed
  T039 alias fixes the aperture extent and paired region. A window exists only
  when the header symbol, the T039 region, and the T039 secure-view alias all
  agree. Everything else is explicit `UNAVAILABLE` plus a reason.
- The secure/non-secure partition inside an aperture and the non-secure-callable
  region are configured at runtime (`FLASH_SECWM*` fields and option bytes), so
  the snapshot records `UNRESOLVED_CONFIGURATION_DEPENDENT` /
  `NSC_REGION_CONFIGURATION_DEPENDENT` with the pinned configuration-register
  evidence. No partition boundary, NSC address, veneer address, or instruction
  semantic is invented. A caller-supplied partition size is explicit input, never
  a derived fact.
- STM-019: every exact part keeps its explicit `PLANNED` state. The composer and
  veneer planner return `PLANNED` and never promote a device.
- STM-009/STM-011/STM-020: T039 remains the sole owner of memory/topology facts;
  this layer references the plan aliases without mutating the plan.
- `ParserLimits` and `CancellationToken` bound the loader and the veneer
  evaluator; the loader rejects a duplicate window id, overlapping alias
  apertures, a source header missing from the provenance list, an unknown
  attribute/kind, an out-of-range window, a non-curated or duplicate record, a
  root-pin mismatch, a schema mismatch, truncated input, and digest tamper.

## Implemented model

### Deterministic generator and pinned snapshot

`scripts/generate-stm32-security-domains.py` consumes five pinned inputs and
verifies each digest before use:

- `catalogs/stm32/2026-09-29/curated-catalog.json` (`afc66a47…`),
- `catalogs/stm32/2026-09-29/selection.json` (`1d4b971f…`),
- `.embedra/evidence/tasks/T039-memory-header-evidence.json` (`491c148f…`),
- `catalogs/stm32/2026-09-28/cmsis-interrupts.json` (`2c312786…`),
- `catalogs/stm32/2026-09-29/memory-plans.json` (`00def281…`).

For every curated exact part it reads the pinned CMSIS header declarations and
keeps a secure alias only when (a) the header declares a literal `*_BASE_S`, (b)
the matching `*_BASE_NS` is literal, (c) a validated T039 region starts at that
non-secure base, and (d) at least one T039 alias starts at the secure base and
targets that region with an agreeing extent. The emitted window carries the
header repository/commit/path/SHA-256/line/declaration, the reviewed T039 alias
ids, and the paired region id. A secure symbol with no reviewable pair is listed
in `unresolvedAliasSymbols` with a reason instead of being guessed. Parts with
no literal secure alias are `UNAVAILABLE`; the reason distinguishes a header
that only declares non-secure-suffixed aliases
(`NON_SECURE_SUFFIXED_ALIASES_ONLY`, for example `STM32H503RBT6`) from a header
with no secure/non-secure aliases at all.

The snapshot records `aliasViewParts: 19`, `unavailableParts: 34`, the five
source pins, and per-part records. The generator is deterministic: regeneration
reproduces the committed bytes, and the companion
`security-domains.sha256` is
`08da45f506d670df3ed042243513d0a3751d07cce2b256cb2c46cd7db23ee3e9`.

### Catalog loader

`Stm32SecurityCatalog.load`/`parse` verifies the committed digest, the closed
root/record/window/NSC/veneer schemas, the five pinned source digests, exact-part
membership in the digest-pinned selection, unique exact parts, recorded
alias/unavailable counts, and every model invariant before exposing records.
`requireRecord` resolves only an exact part id; a family or wildcard query is an
explicit failure. The model itself rejects an unknown attribute, a
non-secure-callable alias aperture, a missing alias pair on an alias aperture, a
window outside the 32-bit space, duplicate window ids, overlapping alias
apertures, a header path absent from the provenance list, a transition outside
its NSC boundary, and an unavailable record that carries data.

### Plan composition

`Stm32SecurityPlanner.compose(Plan, Record[, securePartitions])` returns a new
`SecurityMap`; the T039 plan (regions, aliases, topology) is never modified.
Composition fails closed with stable diagnostics on: an unavailable part
(`SECURITY_NOT_AVAILABLE`), a part mismatch (`SECURITY_PART_MISMATCH`), an
unresolved T039 configuration (`SECURITY_PLAN_CONFIGURATION_UNRESOLVED`), a
window overlapping an MCU region (`SECURITY_WINDOW_OVERLAP`), a window beyond
the 32-bit space (`SECURITY_WINDOW_OUT_OF_SPACE`), a window whose T039 alias is
missing or targets another region (`SECURITY_WINDOW_UNPAIRED`), a window whose
extent disagrees with its T039 alias (`SECURITY_WINDOW_RANGE_MISMATCH`), an
unknown partition input (`SECURITY_CONFIGURATION_UNKNOWN`), an input on a
non-secure boundary (`SECURITY_CONFIGURATION_NOT_APPLICABLE`), an input outside
`0 < size <= window` (`SECURITY_CONFIGURATION_OUT_OF_RANGE`), a veneer outside
its NSC boundary (`SECURITY_VENEER_OUTSIDE_NSC`), and an unknown veneer target
(`SECURITY_VENEER_TARGET_UNKNOWN`). A configured secure partition keeps the
fixed alias aperture as the range and records the explicit `secureBytes`;
without input, `secureBytes` is `-1` and `partitionResolved()` is false.

### Veneer handling (pure)

`Stm32VeneerTransition` models one secure/non-secure callable transition with an
explicit non-secure-callable range, a secure target region id, and an evidence
id; instruction semantics are deliberately absent. `Stm32VeneerPlanner.plan`
evaluates bounded caller candidates and matches only when a pinned
non-secure-callable window covers the address, a declared transition covers it,
and the candidate's evidence id equals the transition's. Everything else is
rejected with `NSC_REGION_NOT_PINNED`, `VENEER_OUTSIDE_NSC`,
`VENEER_UNEVIDENCED`, or `VENEER_EVIDENCE_MISMATCH`; non-match details are
bounded to 128 with one overflow summary, the candidate list is bounded by
`ParserLimits.maxObjects`, cancellation is cooperative, and the evaluation
result always reports `PLANNED`. The shipped snapshot contains no NSC boundary
because the pinned sources fix it only through runtime configuration, so every
candidate against the shipped catalog is an explicit rejection rather than a
fabricated match.

### Ghidra adapter boundary

Applying security-domain facts to a Ghidra program is deliberately out of scope,
as the task allows. A partition boundary and NSC/veneer addresses are not
resolvable from the pinned sources, so no adapter is added and no integration
test changes are required. This matches T042's recorded `NO_ADAPTER` precedent.

## Preserved boundaries and limitations

- T039 memory plans (`00def281…`), the T040 applicability artifact
  (`be795ab0…`) and device-data packs, T041 vector behavior, T042 board profiles,
  and T043 signature packs are unchanged.
- All 53 curated parts remain `PLANNED`; T044 promotes no support state. The
  `securityStatus` of every curated catalog record remains `UNKNOWN`.
- Only fixed secure alias apertures are represented. A secure partition inside a
  bank, an NSC boundary, a veneer address, and the corresponding instruction
  semantics remain configuration-dependent or instruction-dependent and are
  never guessed.
- `NON_SECURE` and `NON_SECURE_CALLABLE` are part of the model but no shipped
  record claims them: the non-secure memory is already T039's plan, and no pinned
  source fixes an NSC boundary.
- No Ghidra program mutation is performed, so no partition, alias block, or
  veneer is applied to a real program by T044.
- The secure-alias windows reuse the reviewed T039 alias extents; the T039 plan
  remains the single source of the aperture extent, and the snapshot and the plan
  must agree or composition fails closed.

## Failures encountered and resolved

- The first focused Java run failed one generator assertion because the window
  cited the evidence-index key (`cmsis-device-h5/Include/…`) instead of the
  repository-relative header path; the generator now carries the pinned
  `path` field, which is what the loader and tests compare.
- Three loader tests initially matched exception text that named the schema
  mismatch differently (`Unknown security window value`, `schema`), and the
  truncated-input test expected `IOException` where `StrictJsonParser` raises a
  typed `DiagnosticException`. The tests were corrected to assert the actual
  fail-closed diagnostics; no production check was weakened.
