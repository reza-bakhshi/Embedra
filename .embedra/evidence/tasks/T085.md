# T085 Evidence — Target-Aware Full-Flash Planning for ESP32-S31, ESP32-P4, and ESP32-E22

## Status

`COMPLETE` on 2026-10-13. T085 implements and independently verifies the full-flash planning
path for `ESP32-P4` (chip ID 18), `ESP32-S31` (chip ID 32), and `ESP32-E22` (chip ID 31).
Each target is registered with an independent layout profile (`RISCV:LE:32:default`, `gcc`,
bootloader at `0x0000`, 64 KiB MMU page size). Silicon documentation gaps and preliminary
status for S31 and E22 are explicitly recorded in accordance with ESP-016 and ESP-027.

## 1. Deliverables

1. **Flash Layout Provider Registrations**:
   - `EspFlashLayoutRegistry`:
     - Registered `ESP32-P4`: chip ID 18, RISC-V RV32IMAFCP, reference `esptool/targets/esp32p4.py`.
     - Registered `ESP32-S31`: chip ID 32, dual-core RV32, reference `esptool/targets/esp32s31.py`.
     - Registered `ESP32-E22`: chip ID 31, dual-core RV32, reference `esptool/targets/esp32e22.py`.
   - With this registration, all 14 cataloged ESP32-branded series have dedicated layout providers
     in `EspFlashLayoutRegistry`.

2. **Silicon Gaps and Support Status**:
   - `ESP32-P4`: Fully specified silicon with authoritative pinout, bootloader, and MMU memory
     mapping in ESP-IDF v6.0 and esptool v5.4.0 (`soc/esp32p4/include/soc/soc.h`).
   - `ESP32-S31`: Preliminary silicon parts (`ESP32-S31NRV16`, `ESP32-S31NRV32`). Firmware chip ID 32
     is pinned in esptool v5.4.0, but public technical reference manuals and errata remain preliminary.
     Retained `PLANNED` for exact variant promotions per ESP-016.
   - `ESP32-E22`: Preliminary silicon part (`ESP32-E22`). Firmware chip ID 31 is pinned in esptool
     v5.4.0, but memory mapping is restricted. Retained `PLANNED` for exact variant promotions per ESP-016.

3. **Automated Verification**:
   - `EspS31P4E22FullFlashTest` (`src/test/java/io/github/rezabakhshi/embedra/formats/esp/EspS31P4E22FullFlashTest.java`):
     - Validates layout profiles for `ESP32-P4`, `ESP32-S31`, and `ESP32-E22`.
     - Plans `default-factory.bin` for each target and verifies executables (`bootloader` and `factory`).
     - Verifies auto-detection of chip ID and provider from candidate header at `0x0000`.
     - Verifies custom table offsets (`0x10000`) and encrypted OTA partitions (`assets`).
     - Verifies rejection of corrupted partition MD5 checksums (`ESP_PARTITION_MD5_MISMATCH`)
       and wrong chip IDs (`ESP_CHIP_MISMATCH`).
