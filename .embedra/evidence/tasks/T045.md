# T045 Evidence — STM32 dual-core/heterogeneous workspace planning

## Status

`COMPLETE` on 2026-10-02. T045 adds a pure, evidence-gated STM32 dual-core /
heterogeneous workspace layer in `targets/stm32/workspace`. A workspace plan
references the validated T039 `Stm32MemoryPlanner.Plan` and the T044
`Stm32SecurityRecord` for the same exact part without mutating either, assigns
one program slot per independently supplied executable domain, attributes
shared versus private memory only from the pinned `sharedAccess` facts, reuses
the pinned IPCC mailbox and HSEM hardware-semaphore register
windows and the pinned `RELEASES_FROM_RESET` boot order as typed cross-program
references with provenance, and keeps every unresolved configuration-dependent
view explicit. The curated scope carries exactly two pinned multi-core
executives, `STM32WB55RGV6` and `STM32WB15CCU6` (Cortex-M4 application core
plus Cortex-M0+ radio core); every other cataloged part, including all four
single-Cortex-M7 H7 parts, is planned as explicit `UNAVAILABLE` with a reason
and no invented second core, image, mailbox, semaphore, or boot order. No Ghidra
adapter is added (`NO_ADAPTER_PURE_PLAN_ONLY`, as T042/T044 did), no snapshot
or generator is added (both pinned inputs already carry per-exact-part digest
checks), and all 53 curated parts remain `PLANNED`; T039-T044 artifacts,
device-data packs, vector behavior, board profiles, signature packs, security
domains, and every support state are unchanged.

The repository builds 331 unit tests and 93 real-Ghidra integration tests, and
the STM32 Python suite reports 131 tests (`OK (skipped=4)`, the four
pre-existing optional pinned-source checks) plus 4 ESP Python tests. The
reproducible completion gate passes with two clean, uncached 22-action builds
and a byte-identical 4,294,974-byte extension ZIP, SHA-256
`6ad9a71f94f5af9a0cd9777fd2f2e9b7dc385bde9958b77c2cf2a70265fa6133`.

## Scope and invariants

- The pure/adapter boundary holds. `Stm32WorkspacePlan` and
  `Stm32WorkspacePlanner` live under `targets.stm32.workspace`; they import
  `core`, `memory`, and `security` model classes only and never import a
  Ghidra API. Ghidra mutation remains out of scope.
- STM-009/STM-011/TOPO-004: core ownership is explicit and separate. The
  shared-image application core plans the user-supplied flash image; the
  independently supplied radio core plans a separate program slot whose image
  domain is explicitly `UNAVAILABLE_INDEPENDENTLY_SUPPLIED` and never carries
  an invented range: the CPU2 bytes are not part of the pinned sources, and no
  second flash image is duplicated. Physical RAM is never duplicated: shared
  and private attribution restates the T039 `sharedAccess` facts per region.
- STM-019: every exact part keeps `PLANNED`; `supportState()` is `PLANNED` for
  both statuses and composition never promotes.
- STM-020/TOPO-002/TOPO-003: cores, roles, ISA/language/compiler ids, shared
  memory, mirrors, mailboxes (IPCC `0x58000C00..0x58001000`), semaphores (HSEM
  `0x58001400..0x58001800`), and the CPU1-releases-CPU2 boot order all come
  from the digest-pinned T039 plan (`00def2817b…`) and are re-emitted with the
  confidence and evidence of their pinned source. No family or wildcard
  inference exists anywhere in the composer.
- TOPO-001/TOPO-005: only `CPU_CORE` nodes receive program slots; the pinned
  factory boot context stays a referenced node and never becomes a
  fabricated program. The CPU2 reset-vector fetch view (C2BOOT, C2OPT/SBRV)
  is an explicit `UnresolvedView`; no range is invented for it.
- The workspace plan never mutates its inputs: composition holds the same
  `Stm32MemoryPlanner.Plan` and `Stm32SecurityRecord` objects (asserted by
  identity in tests) and rebuilds nothing from the T044 windows. When a T044
  record is pinned, the security map is composed through
  `Stm32SecurityPlanner.compose` so every T044 invariant still applies; the
  two multi-core parts are TrustZone-`UNAVAILABLE` and reference their record's
  explicit reason.

## Implemented model

### `targets/stm32/workspace/Stm32WorkspacePlan`

Immutable record for one exact part with status `MULTI_CORE_PINNED` or
`UNAVAILABLE`. A pinned plan carries:

- one `ProgramSlot` per independently supplied executable domain, holding the
  pinned T039 node id, role, firmware relationship (`SHARED_IMAGE` or
  `INDEPENDENT_IMAGE`), instruction set, Ghidra language/compiler ids, and
  security domain of its `ProcessorNode`;
- an `ImageDomain`: `PINNED_DEVICE_IMAGE` with the reviewed T039 FLASH region
  range for the shared-image core, or `UNAVAILABLE_INDEPENDENTLY_SUPPLIED`
  with a data-driven reason (independently supplied firmware; pinned release
  mechanism) and no range;
- per-region `MemoryView`s with `Ownership.PRIVATE`/`SHARED` and
  peer-slot sets derived per region from the pinned `sharedAccess` map only
  (WB55/WB15: FLASH private to CPU1; SRAM1 shared CPU1/CPU2 read/write;
  SRAM2A/SRAM2B private to CPU2 exactly as T039 reviews underclaiming CPU1);
- `UnresolvedView`s for configuration-dependent facts (the CPU2 fetch view);
- typed `CrossProgramReference`s: `BOOT_HANDOFF` (mechanism and evidence
  only, never an invented range), `SHARED_MAILBOX` and `SHARED_SEMAPHORE`
  (the pinned peripheral register windows), and `SHARED_MEMORY` (the pinned
  shared bank plus its reviewed mirror ranges);
- two `VERIFIED_CHECKSUM` evidence entries pinning the T039 memory-plan digest
  and the T044 security-domain digest.

An `UNAVAILABLE` plan carries only a reason
(`SINGLE_CORE_EXECUTION_TOPOLOGY: … no second core or coprocessor image exists
in the pinned sources`). The record constructors reject duplicate slots or
references, unknown or self-looping reference endpoints, unknown view peers,
duplicate or overlapping views inside a slot, `BOOT_HANDOFF` ranges, shared
references without ranges, references or evidence that are empty, ranges
outside the 32-bit space, a pinned plan with a reason or without both program
slots and cross-program references, and an unavailable plan with any workspace
data.

### `targets/stm32/workspace/Stm32WorkspacePlanner`

`compose(plan, record[, configurationInputs])` fails closed with stable
`WORKSPACE_*` diagnostics:

`WORKSPACE_PART_MISMATCH`, `WORKSPACE_CONFIGURATION_UNKNOWN` (no workspace
configuration key is pinned, so any input is rejected),
`WORKSPACE_PLAN_CONFIGURATION_UNRESOLVED`, `WORKSPACE_CORES_AMBIGUOUS`
(indistinguishable role+ISA cores), `WORKSPACE_IMAGE_DOMAIN_AMBIGUOUS`
(several shared-image cores), `WORKSPACE_IMAGE_DOMAIN_UNDETERMINED` (no
shared-image core, or a second core without a pinned independent image),
`WORKSPACE_IMAGE_UNDETERMINED` (FLASH region count other than one),
`WORKSPACE_MEMORY_UNATTRIBUTED` (non-RAM core attribution, unknown participant,
a core with no
pinned memory attribution, or a shared view without the pinned T039
shared-memory backing), `WORKSPACE_SLOT_RANGE_OVERLAP` (slots overlapping
outside a documented shared range), `WORKSPACE_BOOT_ORDER_UNPINNED`,
`WORKSPACE_BOOT_ORDER_AMBIGUOUS`, `WORKSPACE_MAILBOX_UNPINNED`,
`WORKSPACE_SEMAPHORE_UNPINNED`, and `WORKSPACE_COMMUNICATION_RANGE_UNPINNED`.
Slot ids derive from the pinned node ids (`cpu1-program`, `cpu2-program`);
overall workspace-level diagnostics and the boundary checks reuse the review
lessons (typed codes, constructors that reject duplicates and overlaps,
per-part binding).

### Ghidra adapter boundary

Applying workspace facts to a Ghidra program is deliberately out of scope.
The CPU2 program exists only when its independently supplied image is
supplied by the user, so there is no complete program pair to which
cross-program navigation could be applied without inventing content. No
adapter, no integration test, and no mutation are added, matching the T042
and T044 `NO_ADAPTER` precedent. The pure plan and its cross-program
references are the navigation contract for a later task; this choice is
recorded as `NO_ADAPTER_PURE_PLAN_ONLY`.

### Failures encountered and resolved

- The first planner version accumulated peer slots per core instead of per
  region, so the CPU2-only SRAM2A/SRAM2B views were emitted `SHARED`. The
  WB55/WB15 attribution regressions caught it; peers now derive per region
  from that region's own `sharedAccess` participants, and the per-core
  validation checks attribution coverage only.
- Two checkstyle `EmptyLineSeparator` violations in the new test file were
  repaired; the checks now pass.
- A test initially expected `partitionResolved()` for a security window with
  no partition input; the correct expectation is that the window stays
  unresolved, and the test was corrected (no production check was weakened).

## Preserved boundaries and limitations

- T039 memory plans (`00def2817b…`), the curated catalog (`afc66a47…`), the
  T040 applicability artifact (`be795ab0…`) and device-data packs, T041 vector
  behavior, T042 board profiles, T043 signature packs, and the T044 security
  snapshot (`08da45f5…`) are unchanged.
- All 53 curated parts remain `PLANNED`; T045 promotes no support state and no
  per-input-format/feature state.
- The curated scope has no dual-core H7 part: H735/H750/H7S3/H7S7 are single
  Cortex-M7 executives, so their workspace plans are explicit `UNAVAILABLE`
  results. Wiring a future H745/H755-class device requires pinned per-part
  evidence of its own (STM-020), exactly as T039's per-record profiles do.
- The workspace does not place bytes: no CPU2 image, range, size, mailbox
  content, semaphore token, or boot timestamp is invented. The 0x10000000
  SRAM2 mirror views stay T039 plan facts referenced through the plan; no new
  per-core attribution is claimed for them.
- No Ghidra workspace mutation, cross-program Ghidra reference, or program
  creation is performed; the plan is the only artifact.
