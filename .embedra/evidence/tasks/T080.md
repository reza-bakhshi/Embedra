# T080 Evidence — Audit ESP32-Branded Series Full-Flash Capability Matrix and Boundary Specification

## Status

`COMPLETE` on 2026-10-13. T080 executes the technical audit of every ESP32-branded
series in the generated catalog against pinned official bootloader, partition,
image, flash-origin, and embedded-flash documentation; records a per-series and
per-exact-variant capability matrix with documented unknowns; preserves strict
segregation of legacy ESP8266 devices; inventories current hardcoded ESP32-S3
assumptions across shared classes; and specifies the common layout provider
architecture planned for T082 in accordance with `Embedra-SpecKit.md` (US4A,
ESP-015 through ESP-027, Section 8.1, and Section 12).

## 1. Deliverables

1. **Audit Document & Capability Matrix**:
   - `docs/esp-full-flash-audit.md`:
     - Documents all 14 ESP32-branded series cataloged in Embedra (`ESP32`, `ESP32-S2`,
       `ESP32-S3`, `ESP32-S31`, `ESP32-P4`, `ESP32-C2`, `ESP32-C3`, `ESP32-C5`,
       `ESP32-C6`, `ESP32-C61`, `ESP32-E22`, `ESP32-H2`, `ESP32-H21`, `ESP32-H4`).
     - Details exact CPU architecture, ISA, Ghidra language binding, chip ID,
       bootloader start offset, default partition table offset, MMU page size (64 KiB),
       virtual address mapping windows (DROM and IROM), and maximum supported flash size.
     - Details per-exact-variant breakdown across all 53 catalog silicon parts.
     - Explicitly documents unknowns and preliminary silicon status for `ESP32-S31`,
       `ESP32-E22`, and `ESP32-H4`.
   - `.embedra/evidence/tasks/T080-capability-matrix.json`:
     - Machine-readable JSON artifact conforming to schema `urn:embedra:schema:esp-full-flash-capability-matrix:1`.
     - Indexes 14 series, 53 silicon records, ESP8266 segregation facts, S3 hardcoded
       assumptions inventory, and the provider contract specification.

2. **Segregation of ESP8266 Legacy Format**:
   - ESP8266 is explicitly excluded from ESP32-branded full-flash workflows per ESP-020,
     ESP-022, and ADR 0025:
     - No extended image header or 16-bit chip ID in firmware images.
     - No partition table structure (`0x50AA` magic / `0xEBEB` MD5 trailer).
     - Static non-partitioned flashing offsets (`0x00000`, `0x01000`, `0x10000`, `0x40000`, `0x81000`).
     - Distinct Xtensa LX106 Harvard architecture core with 1 MiB mapping banks.

3. **Inventory of Current S3 Hardcoded Assumptions**:
   - Documented in `docs/esp-full-flash-audit.md` (§6) and JSON matrix:
     - `EspFullFlashWorkspacePlanner`:
       - `ESP32_S3_CHIP_ID = 9` constant at line 21.
       - Hardcoded bootloader start at offset `0` at line 50.
       - Hardcoded chip ID check `9` during image parsing at line 112.
     - `EspPartitionTableDiscovery`:
       - Static `DEFAULT_OFFSET = 0x8000` and `TABLE_SIZE = 0x1000`.
       - Unbounded scan loop starting at offset `0` across entire flash.
     - `EspApplicationImageLoader`:
       - Direct invocation of `EspFullFlashWorkspacePlanner.plan()` assuming S3.
       - S3-specific option and enrichment strings (`APPLY_ESP32S3_PACKS_OPTION`, `ENRICHMENT_OPTIONS`).
       - Homogeneous CPU architecture assumption across all workspace programs.

4. **Architectural Specification of Common Provider Interface**:
   - Documented in `docs/esp-full-flash-audit.md` (§7):
     - `EspFlashLayoutProfile`: Immutable data model encapsulating series, chip ID,
       language binding, bootloader and partition table offset rules, MMU page size,
       and max flash size.
     - `EspFlashLayoutProvider`: Pure provider interface supplying target layout rules,
       offset validation, and bootloader/application image validation.
     - `EspFlashLayoutRegistry`: Dynamic lookup registry by chip ID or series name.
     - Decoupled `EspFullFlashWorkspacePlanner` workflow to be implemented in T082.
