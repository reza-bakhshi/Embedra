# T048 Evidence — STM32 firmware diff and CTF enrichment using the shared analyzers

## Status

`COMPLETE` on 2026-10-02. T048 adds a pure, evidence-gated STM32 firmware diff
and CTF enrichment layer in `analyzers/stm32`, consuming the implemented shared
analyzers without duplicating or weakening them. `Stm32FirmwareArtifact` carries
the confirmed comparison metadata of one validated STM32 image (the bound exact
part, the caller's artifact identity and role, the confirmed image extent reusing
the T041 `ImageRange` contract, the validated content SHA-256, and the confirming
import provenance). `Stm32FirmwareDiffAnalyzer` applies the shared T025 diff
contract — the `EspArtifactChangeKind` vocabulary and the ADR-0017 rule that
content digests are compared before physical extents — over confirmed STM32
artifacts with per-part binding and typed diagnostics.
`Stm32CtfEnrichmentAnalyzer` applies the shared analyzers to STM32 inputs and
produces ranked, provenance-bearing leads. All 53 curated parts remain
`PLANNED`; T039-T047 artifacts, every pinned snapshot, every device-data and
signature pack, and every support state are unchanged. No Ghidra adapter is
added (`NO_ADAPTER_PURE_PLAN_ONLY`).

The repository builds 380 unit tests (25 new T048 tests, plus 2 hardening tests) and 104
real-Ghidra integration tests, and the STM32 Python suite reports 131 tests
(`OK (skipped=4)`, the four pre-existing optional pinned-source checks) plus 4
ESP Python tests. The reproducible completion gate passes with two clean,
uncached 22-action builds and a byte-identical extension ZIP, SHA-256
`ba872aeaf067ae07fd25e6e02c0c80edf485caddab1eb10fad056250dc0e8bbf`
(4,433,407 bytes; the size change over T047 comes from the packaged
architecture and support-matrix descriptions).

## Scope and invariants

- The pure/adapter boundary holds. All T048 classes live under
  `analyzers.stm32`; they import `core`, `analyzers.esp`, and
  `targets.stm32` model classes only and never import a Ghidra API. No Ghidra
  mutation exists in this task.
- Shared-analyzer reuse is verbatim and asserted: signature identification runs
  through the T043 `Stm32SignatureMatcher.match` with a shared
  `Stm32SignatureContext`; the enrichment report carries the shared
  `Stm32SignatureMatchReport` object unchanged, and a test asserts the report
  equals a direct `Stm32SignatureMatcher.match` call on the identical inputs.
  The T043 evidence gates are reused as-is: missing compiler/optimization/family
  evidence stays the explicit `EVIDENCE_MISSING` non-match, an unavailable index
  stays `INDEX_UNAVAILABLE`, an unmatched function stays `NO_MATCH`, and none of
  them is ever reported as a finding.
- The T025 diff contract is consumed as a contract: the shared
  `EspArtifactChangeKind` vocabulary (unchanged/moved/modified/added/removed)
  and the digest-before-extent ordering rule are applied over STM32 artifacts.
  The ESP analyzer itself is untouched and unweakened; its records cannot accept
  STM32 image extents, so the classification is re-expressed over the T041
  `ImageRange` contract instead of duplicating the ESP record shape.
- Never invent a diff result, lead, confidence, symbol, or memory fact. TrustZone
  evidence is consumed only from a digest-pinned T044 `Stm32SecurityRecord`;
  logging/assert recovery is the one shared contract this layer cannot permit
  for STM32 inputs (ADR 0015 requires a resolved target plus constant
  tag/format pointers, and no STM32 logging/assert target is pinned anywhere in
  this repository — the shipped F1 pack was verified in-repository to contain no
  assert/printf/log-named signature), so it stays the explicit
  `stm32-logging-assert-recovery` capability gap and produces no lead.
- Per-part binding: every confirmed artifact and the optional security record
  must bind to one exact part present in the digest-pinned curated selection
  (`Stm32CuratedPartIds`, pinned selection SHA-256 `1d4b971f…`); mixed or
  uncurated binding fails closed with typed `DIFF_*`/`ENRICHMENT_*` diagnostics
  before any comparison or lead is produced.
- A diff or lead is a hint with provenance and bounded confidence; it never
  proves exploitability or device support, and no T048 detector produces secret
  material (`secret` is false everywhere; the shared redaction rules apply to
  exports, not re-invented here).
- `ParserLimits`, `CancellationToken`, `AddressRange`, the T041 `ImageRange`
  contract, the T043 signature evidence gates, the T044 security record
  contract, and the exact-part digest-pinned selection contract are reused
  throughout.
- STM-019: every exact part keeps `PLANNED`; nothing in the diff or enrichment
  promotes a support state.

## Implemented model

### `analyzers/stm32/Stm32FirmwareArtifact`

Immutable validated comparison metadata: non-blank `exactPart`/`id`, a
`BASELINE` or `CANDIDATE` role, a non-empty 32-bit `imageRange` (T041
`ImageRange`), a validated 64-hex lowercase `sha256`, and non-empty confirming
`Evidence` (provenance must be established; otherwise construction fails
closed). No firmware bytes are retained.

### `analyzers/stm32/Stm32FirmwareDiffAnalyzer`

`analyze(context, limits, token)` enforces the shared limits and cancellation,
binds the context (baseline and candidate artifacts must share one exact part —
`DIFF_EXACT_PART_MISMATCH`; the shared part must be in the digest-pinned curated
selection — `DIFF_EXACT_PART_UNCURATED`), and classifies with the T025
ordering: absent baseline/candidate yields `ADDED`/`REMOVED`; differing digest
yields `MODIFIED` even when the extent also differs; equal digest with a
different extent yields `MOVED`; otherwise `UNCHANGED`. The diff carries
`VERIFIED` confidence, a `VERIFIED_CHECKSUM` classification statement naming
both artifact ids and the bound part, and the artifacts' own confirming
evidence restated (deduplicated, deterministic order). No cross-part,
cross-image, or function/string-level comparison is invented here; those stay
T056-T064.

### `analyzers/stm32/Stm32CtfEnrichmentAnalyzer`

`analyze(context, pack, limits, token)` enforces the shared limits and
cancellation, binds the context (`ENRICHMENT_ARTIFACT_PART_MISMATCH`,
`ENRICHMENT_PART_UNCURATED`, `ENRICHMENT_SECURITY_PART_MISMATCH`), then runs:

- the signature pass through `Stm32SignatureMatcher` — the shared
  `Stm32SignatureMatchReport` (matches, bounded non-matches, counts) is carried
  verbatim in the report, and every match becomes a
  `STM32_SIGNATURE_LIBRARY_FUNCTION` lead with the match's own confidence and
  evidence;
- the security pass over the optional T044 record — `PINNED` restates the
  record's secure alias apertures with pinned header provenance,
  `UNAVAILABLE` carries the record's pinned reason, and `NOT_SUPPLIED` records
  a missing confirmed record; a confirmed image extent falling entirely inside
  a pinned `SECURE` alias aperture becomes an `STM32_IMAGE_IN_SECURE_ALIAS`
  lead (`MEDIUM`, `DERIVED`), while plain-flash or partial extents produce no
  lead;
- the explicit logging/assert capability gap.

Leads are ranked deterministically by severity (`HIGH`, `MEDIUM`, `LOW`,
`INFO` — closed set), then code, then address; contexts reject duplicate
artifact ids or roles, duplicate candidate function addresses, and candidate
addresses beyond the 32-bit space; every list is immutable; repeated runs are
deterministic.

### Failures encountered and resolved

- The first targeted test run failed compilation with 100 absent production
  symbols (test-first red state); the implementation then brought all 25 tests
  green.
- The nested `Diagnostic` enums initially shadowed the core `core.diagnostic.
  Diagnostic` factory inside the two analyzers; the core type is now consumed
  through a static single-type import of its `error` factory, and the checkstyle
  line-length violations that introduced are gone.
- `Stm32SecurityEvidence` initially rejected the `null` reason a pinned section
  legitimately carries; the constructor now requires `null` for `PINNED` and a
  non-blank reason for the explicit unavailability statuses, matching the
  `Stm32SecurityRecord` convention.
- Four enrichment security tests initially bound the analyzed part to a
  two-part in-test selection lambda that excluded the security-snapshot parts;
  they now bind through the real digest-pinned selection, and the mixed-artifact
  binding case uses a baseline-role artifact so the typed part-mismatch
  diagnostic (not the duplicate-role rejection) is exercised.

## Preserved boundaries and limitations

- T039 memory plans (`00def2817b…`), the curated catalog (`afc66a47…`), the T040
  applicability artifact (`be795ab0…`) and device-data packs, T041 vector
  behavior, T042 board profiles (`78a3e0e4…`), the T043 signature pack and its
  generation path, T044 security domains (`08da45f5…`), the T045 workspace
  layer, the T046 wireless layer, and the T047 external-memory layer are
  unchanged.
- All 53 curated parts remain `PLANNED`; T048 promotes no support state.
- The diff compares confirmed artifact-level metadata (content digest and image
  extent) exactly as the shared T025 contract does; function, string, symbol,
  and memory-level diffing remain T056-T064 and are not claimed.
- Signature leads require caller-recorded family/compiler/optimization evidence
  and the digest-pinned F1 pack; other families, compilers, optimizations, or
  library versions stay `INDEX_UNAVAILABLE`.
- Logging/assert recovery is explicitly unavailable for STM32 inputs in this
  repository; the gap is a stable capability entry, not a silent absence.
- Security leads restates pinned alias apertures and confirmed image extents
  only; the secure/non-secure partition and NSC boundaries stay
  configuration-dependent, so no partition, NSC, or veneer lead is possible from
  the pinned data.
- No firmware bytes, secrets, or invented symbols enter any report; the reports
  are pure models with no export path of their own.
