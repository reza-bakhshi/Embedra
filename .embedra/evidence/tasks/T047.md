# T047 Evidence — STM32 external-memory loaders and OCTOSPI/FMC mapping

## Status

`COMPLETE` on 2026-10-02. T047 adds a pure, evidence-gated STM32
external-memory layer in `targets/stm32/extmem` plus the one Ghidra adapter the
task's loader scope required. `Stm32ExternalMemoryPlanner` pairs the validated
T039 `Stm32MemoryPlanner.Plan` with one confirmed board fact source — the
digest-pinned T042 board profile (resolved from `Stm32BoardCatalog` by exact
part, with an explicit `UNAVAILABLE` plan and pinned reason when the snapshot
carries no profile or an explicitly unavailable one), or a confirmed
user-supplied custom profile (STM-016) — and turns it into an immutable
external-memory mapping plan of controller windows. `planLoad` plans a bounded
external load as a device-offset range against one pinned window and derives
its CPU aperture address; `classifyCpuAddress` classifies a numeric CPU address
against the pinned apertures only. `Stm32ExternalMemoryApplicator` maps pinned
apertures and loads caller-supplied bytes transactionally. All 53 curated parts
remain `PLANNED`; T039-T046 artifacts, every pinned snapshot, every device-data
pack, and every support state are unchanged.

The repository builds 353 unit tests and 104 real-Ghidra integration tests
(12 new pure and 11 new real-Ghidra tests), and the STM32 Python suite reports
131 tests (`OK (skipped=4)`, the four pre-existing optional pinned-source
checks) plus 4 ESP Python tests. The reproducible completion gate passes with
two clean, uncached 22-action builds and a byte-identical extension ZIP,
SHA-256 `0f50ba57c2cd68c112f93f1259de5490f1d0722e9428f74c31cd56ca2aee3bcf`.

## Scope and invariants

- The pure/adapter boundary holds. `Stm32ExternalMemoryPlan`,
  `Stm32CustomBoardProfile`, and `Stm32ExternalMemoryPlanner` live under
  `targets.stm32.extmem`; they import `core`, `board`, and `memory` model
  classes only and never import a Ghidra API. The only Ghidra mutation lives in
  `ghidra/stm32/Stm32ExternalMemoryApplicator`.
- Every window originates from a confirmed fact source: the digest-pinned T042
  board profile (snapshot `78a3e0e4…`, board index `2b9c7c2c…`, per-region
  quoted BSP/CMSIS evidence), or a custom profile whose mandatory
  `USER_ASSERTION` confirmation is the user's own statement. No device,
  controller, window, alias, size, permission, board link, or address is ever
  invented; composition and loading fail closed otherwise.
- STM-016: a custom profile adds external flash/RAM and boot offsets over one
  exact curated part without changing the underlying MCU pack and without
  touching any pinned snapshot. The custom regions reuse the T042
  `ExternalRegion` contract unchanged (`ext-mem` address space, positive size,
  non-blank controller/device, quoted evidence).
- STM-019: every exact part keeps `PLANNED`; `supportState()` is `PLANNED` for
  both plan statuses and nothing promotes.
- The controller window/aperture separation is modeled: a `MappingWindow`
  carries the pinned `ext-mem` aperture (numeric CPU base and mapped device
  extent) separately from device-offset space (`0..size` indices), with
  checked aperture↔device-offset translation. True numeric collisions fail
  closed: a window overlapping an MCU plan region or another window (the
  address-space tag is ignored for collision checks, exactly as T042 does), a
  window beyond the 32-bit space, and a boot offset outside every external
  region. The controller-family projection onto the modeled
  OCTOSPI/XSPI/QUADSPI/FMC families is mechanical from the confirmed
  controller name; anything else is `EXTERNAL_CONTROLLER_UNRECOGNIZED`, never
  a fabricated controller.
- The adapter binds to the program-recorded exact part: a program that records
  no part, or a different part, fails closed before any transaction opens.
- `ParserLimits`, `CancellationToken`, `AddressRange`, the T042 board-profile
  contracts, and the T039 plan contracts are reused throughout.

## Implemented model

### `targets/stm32/extmem/Stm32ExternalMemoryPlan`

Immutable per-part record with status `EXTERNAL_MEMORY_MAPPED` or
`UNAVAILABLE`, the confirmed `Source` (`PINNED_T042_BOARD_PROFILE` or
`CONFIRMED_CUSTOM_PROFILE`), the board name, the referenced (never-mutated)
T039 MCU plan, sorted disjoint `MappingWindow`s, the carried boot offsets, and
`VERIFIED_CHECKSUM` evidence pinning the T039 memory-plan and T042
board-profile digests (custom profiles additionally carry their
`USER_ASSERTION` entry). The constructors reject a duplicate or overlapping
window, a window beyond the 32-bit space, a mapped plan without source/board/
windows, and an unavailable plan that carries any window, boot offset, board,
or source.

### `targets/stm32/extmem/Stm32ExternalMemoryPlan.MappingWindow`

One controller window: the pinned window id, physical kind (external flash or
RAM), device name, controller name, mechanical `ControllerFamily` projection
(OCTOSPI/XSPI/QUADSPI/FMC, exact prefix rules, unrecognized names fail
closed), the pinned `ext-mem` aperture, the pinned writability, and the quoted
start/size evidence. Pure translation helpers (`coversCpuAddress`,
`coversDeviceOffset`, `deviceOffsetOfCpuAddress`, `cpuAddressOfDeviceOffset`)
keep CPU aperture addresses and device offsets separated; an uncovered
translation fails closed. External windows are never executable (the pinned
T042 `ExternalRegion.executable()` fact is respected through the pinned
writability and non-executable adapters).

### `targets/stm32/extmem/Stm32CustomBoardProfile` (STM-016)

A confirmed user-supplied profile with a board name, an exact curated part
(verified against the digest-pinned selection at load), regions reusing the
T042 `ExternalRegion` contract, optional boot offsets, and a mandatory
`USER_ASSERTION` confirmation evidence. `load` parses a bounded user JSON file
(schema `urn:embedra:schema:stm32-custom-board-profile:1`, closed root/region/
boot/confirmation schemas) and fails closed on a missing or non-regular path,
oversized input, schema mismatch, closed-field mismatch, unknown kind,
non-integer numbers, a non-curated part, a blank or missing confirmation, a
duplicate region id, overlapping regions, truncated JSON, and cancellation.
The constructors reject an empty region set, duplicate ids, overlapping
regions, and a non-`USER_ASSERTION` confirmation. No pinned snapshot is read
for mutation and no digest is claimed for a custom file.

### `targets/stm32/extmem/Stm32ExternalMemoryPlanner`

`compose(plan, profile)`, `compose(plan, catalog)`, and
`composeConfirmed(plan, customProfile)` fail closed with stable diagnostics:

`EXTERNAL_PART_MISMATCH`, `EXTERNAL_BOARD_PROFILE_AMBIGUOUS`,
`EXTERNAL_CONTROLLER_UNRECOGNIZED`, `EXTERNAL_WINDOW_OVERLAPS_MCU`,
`EXTERNAL_WINDOW_OUT_OF_SPACE`, `EXTERNAL_BOOT_OFFSET_OUT_OF_RANGE`,
`LOADER_NOT_AVAILABLE`, `LOADER_DEVICE_UNKNOWN`, `LOADER_RANGE_EMPTY`,
`LOADER_RANGE_OVERFLOW`, `LOADER_RANGE_BEYOND_LIMITS`, and
`LOADER_ADDRESS_UNCOVERED`.

`compose(plan, catalog)` resolves the part by exact id only: no profile in the
pinned snapshot yields the explicit `UNAVAILABLE` reason
`NO_CONFIRMED_BOARD_PROFILE…`; several profiles yield
`EXTERNAL_BOARD_PROFILE_AMBIGUOUS`; an explicitly unavailable pinned profile
keeps its pinned reason. `planLoad` requires a mapped plan, a known window, a
positive length inside the device extent, and a length within
`maxInputBytes`/`maxExtractedBytes` and a single Ghidra block; it returns the
placement (device id, kind, controller, family, device offset, length, derived
CPU aperture address, pinned writability, pinned window, evidence) and never
reads or places bytes itself. `classifyCpuAddress` returns the covering
window's device, controller, family, device offset, and writability, or fails
closed.

### `ghidra/stm32/Stm32ExternalMemoryApplicator` (the T047 adapter)

Two entry points over one receipt namespace (`Embedra STM32 External Memory`):

- `mapWindows` creates every pinned aperture as an uninitialized memory block
  named `embedra_extmem_<window-id>` with read access, the pinned writability,
  and no execute permission, plus an `IMPORTED` label at the aperture base.
- `loadInto` reads the caller-supplied bytes (exact length required —
  absent, truncated, oversized, or short-read inputs fail closed before any
  transaction opens) and creates one initialized block at the planned CPU
  aperture address with the planned bytes, the pinned writability, no execute
  permission, and a label.

Both: require a 32-bit little-endian ARM program; bind to the recorded exact
part across the raw-import, SVD, interrupt, vector-label, and external-memory
namespaces (`PACK_INCOMPATIBLE` on disagreement,
`PACK_INCOMPATIBLE` when nothing is recorded); run inside one
`GhidraProgramTransaction`; and never remove, split, or overwrite an existing
block. Existing user memory yields `MEMORY_PRESERVED`; a created block that
the user deleted yields `PRESERVED_ABSENT` and is not recreated (receipt names
are persisted, so deleted or renamed created blocks are never resurrected); a
prior load block whose bytes were changed yields `CONTENT_DIFFERS`; a label
name taken elsewhere yields `NAME_CONFLICT`. A matching created block with
identical permissions and bytes is confirmed without changes, so reapplication
is idempotent. Provenance records the exact part, the confirmed source, the
board, the device, and the receipt names. Because existing memory is never
split, `mapWindows` and `loadInto` are alternative workflows for one program:
loading into an already mapped aperture preserves the window and applies
nothing.

### Failures encountered and resolved

- The custom out-of-space case first surfaced the generic `MappingWindow`
  constructor message instead of the typed `EXTERNAL_WINDOW_OUT_OF_SPACE`
  diagnostic; the planner now pre-checks the range before constructing the
  window, and the constructor keeps its own defense-in-depth check.
- The null-confirmation custom-profile case rejected through the record's
  standard `NullPointerException`; the test asserts that exact behavior.
- Two checkstyle violations in the new adapter/test (a merged line and a
  missing method separator) were repaired; the checks now pass.

## Preserved boundaries and limitations

- T039 memory plans (`00def2817b…`), the curated catalog (`afc66a47…`), the
  T040 applicability artifact (`be795ab0…`) and device-data packs, T041 vector
  behavior, T042 board profiles (`78a3e0e4…`), T043 signature packs, T044
  security domains (`08da45f5…`), the T045 workspace layer, and the T046
  wireless layer are unchanged.
- All 53 curated parts remain `PLANNED`; T047 promotes no support state.
- No external-memory fixture corpus exists: the real-Ghidra load tests use
  in-test synthetic bytes against a repository-authored fixture program, so no
  external-device image coverage is claimed. No hardware verification is
  claimed.
- The load path never merges into a mapped aperture: existing blocks are
  preserved and never split or removed, so window mapping and byte loading
  are alternative workflows for one program.
- Custom controller names must project onto the modeled OCTOSPI/XSPI/QUADSPI/
  FMC families; a controller outside those families fails closed rather than
  being modeled. No per-part controller-existence verification exists in the
  pinned data, so a custom profile's controller claim rests on its
  `USER_ASSERTION` confirmation.
- The pinned T042 profiles pin no boot offsets, so the boot-offset paths are
  exercised only through confirmed custom profiles and the planner's shared
  validation.
- External windows are never marked executable and never produce aliases; a
  window's address-space tag stays the pinned `ext-mem` reporting space.
